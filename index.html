02 / Snowflake business case

Can Finance trust today's sales number?

This is the question the Snowflake extension answers. You do not need to understand data platforms to understand the outcome.

The business problem

A Finance Director is preparing the daily trading update.

Orders arrive from the web store, retail outlets and marketplace. A system retry sends one order twice. If that duplicate reaches the report, leadership sees revenue that was never earned and may make the wrong decision.

Question 1
What did we actually sell today?
Question 2
Which sales channel is behind plan?
Question 3
Can Finance explain and defend the number?
Decision protected Do we increase tomorrow's sales target or correct the source issue first?

Without a trusted number, a confident-looking dashboard can still lead to the wrong action.

Before the control

RM1,417.60 appears on the report

The duplicated RM420.00 order is included. Finance spends time checking spreadsheets and asking teams which number is correct.

Risk: overstated revenue and delayed decisions
→
After the control

RM997.60 is ready for review

The duplicate is retained as evidence, excluded from the trusted sales result and made visible for follow-up.

Outcome: a decision-ready number with an audit trail

How the demo maps to Snowflake

Business-first on the surface. Native controls underneath.

The planned implementation uses synthetic data only: a staged source table, a validated trusted-order layer, a quarantine table and a daily sales mart. Dynamic Tables keep the reporting layer current; role-based access and masking protect the people behind the numbers.

  • IngestStage and COPY INTO
  • TransformDynamic Tables and SQL
  • TrustReconciliation and quarantine
  • ProtectRoles, tags and masking
Evidence boundary

This is an inspectable Snowflake delivery design using synthetic sales data. The SQL assets are ready for a Snowflake trial account, but no Snowflake account execution, client data, production security or cost claim is made until it is independently run and evidenced.

Why this discovery tool is useful

It turns a vague data concern into a shared, testable delivery decision.

Instead of starting with platform jargon, the lab gives business and technology teams one realistic incident to discuss: the number is wrong, here is the impact, and here is what must be true before it can be trusted.

For the regional business data owner

Make data ownership practical.

Use the scenario to agree which daily numbers matter, who owns each source, which exceptions require action and what “trusted enough to decide” means for Finance and operations.

  • Prioritise the business decision, not a generic dashboard.
  • Confirm the data-quality rules before development starts.
  • Set a clear exception and escalation process across regions.
Outcome: a shared data contract and a decision-ready reporting requirement.
For the data platform developer

Turn the agreed outcome into a buildable pattern.

Use the same scenario to shape source ingestion, trusted transformations, quarantine handling, access controls, monitoring and acceptance tests before connecting a production source.

  • Translate business rules into SQL checks and reconciliation tests.
  • Design a repeatable raw, trusted and reporting-layer flow.
  • Prove that people see only the data they need.
Outcome: a small, demonstrable delivery slice with clear acceptance criteria.
Shared starting pointThe regional owner defines the decision and trust rules. The platform developer implements and proves them. Both can see the same expected outcome before a larger programme begins.
03 / Architecture

Designed for delivery, not screenshots.

The public experience is a transparent browser simulation. The repository contains Databricks implementation evidence and a Snowflake-ready business-case design.

Source control

One deployable repository

Pipeline code, job resources, access model, tests and operational documentation are versioned together.

Automation

Declarative bundle

Development and production targets are defined as code for repeatable validation and deployment.

Governance

Least-privilege access

Catalog grants, masking design and persona-specific outputs demonstrate governed consumption.

Reliability

Testable recovery

Duplicate delivery, malformed input and late data are documented failure modes, not demo-day surprises.
